# ILSC — Interface-Level Semantic Cohesion

Working repository for the ILSC metric. This package covers **Day 1–3 of the empirical track** (multi-source curation, the
field-availability study, the pair-level co-availability study) plus **Day 1–2
of the metric track** (parser and feature extraction), and the decisions that
came out of them.

Anyone starting from this folder can rebuild everything in about 25 minutes.

---

## 2. Reproducing everything

```bash
# 1. Dependencies
pip install -r requirements.txt
npm install                       # swagger2openapi 7.0.8, used by step (b) only

# 2. Fetch S1 — RAMA threshold benchmark (Bogner et al. 2020), the anchor
#    core.longpaths is REQUIRED on Windows: several RAMA filenames exceed the
#    260-character path limit and the clone fails at checkout without it.
git clone -c core.longpaths=true --filter=blob:none --sparse \
    https://github.com/restful-ma/thresholds.git rama-thresholds
cd rama-thresholds
git sparse-checkout set benchmark-repository/openapi
git checkout 5b0b2a3322d3b2b7c0e0f2c0c0ad0e524e67bf82
cd ..                                   # expect 2,619 files

# 3. Fetch S2 — APIs.guru current snapshot
git clone -c core.longpaths=true --filter=blob:none --sparse \
    https://github.com/APIs-guru/openapi-directory.git openapi-directory
cd openapi-directory
git sparse-checkout set APIs
git checkout f04b8d0bcd39c52e1cf3ad7a5fe744709832ae49
cd ..

# 4. Run
python run_all.py
```

**Pinned commits:** S1 `5b0b2a3322d3b2b7c0e0f2c0c0ad0e524e67bf82` ·
S2 `f04b8d0bcd39c52e1cf3ad7a5fe744709832ae49`.
Without pinning, the corpora change under you and no result is reproducible.

Steps are individually runnable, and the expensive half of `filter.py` is
checkpointed, so a dedup rule can be re-evaluated without re-parsing 6,757
specs:

```bash
python src/filter.py --scan S1     # parse into .cache/  (~4 min)
python src/filter.py --scan S2     # ~6 min
python src/filter.py --merge       # dedup + write       (seconds)
```

Install libyaml (`yaml.CSafeLoader`) or the scan takes roughly ten times longer:

```python
import yaml; print(hasattr(yaml, "CSafeLoader"))
```

## 3. Corpus statistics

Two sources, 6,757 specification files in.

| Stage | Removed | Reason |
|---|---|---|
| a — parse | 49 | malformed file |
| a — structure | 184 | no `paths` or no `info` |
| b — RPC-shaped | 1 | every path identical |
| c — < 3 operations | 1,264 | too small for a pairwise metric |
| d — dedup (within source) | 1,199 | older version of the same API |
| e — dedup (cross-source) | 1,854 | already present in S1 |
| **Surviving** | **2,206** | |

**Composition of the survivors**

| Property | Value |
|---|---|
| S1 (RAMA) / S2 (APIs.guru) | 1,014 / 1,192 |
| OpenAPI 3.x | 2,062 (93.5%) |
| Swagger 2.0 | 144 (6.5%) |
| Operations per service | min 3, median 16, mean 44.4, max 11,422 |
| Total operations | 97,912 |
| Within-service pairs | 77,611,030 |
| Distinct providers | 616 |
| Admin endpoints stripped | 62 across 48 services |
| Strict validation (D-02, n=200) | **97.5% valid** — S1 100%, S2 94.9% |

> **The version split is an artefact, not a fact about the world.** RAMA
> converted its inputs to OpenAPI 3 upstream, so S1 is 100% 3.x by
> construction. S2 alone is 26.9% Swagger 2.0. Never read the pooled split as a
> statement about how authors publish (D-10).

**Provider concentration** — the largest threat to external validity, and it
differs sharply by source:

| | Services | Providers | AWS + Google + Azure |
|---|--:|--:|--:|
| S1 (RAMA) | 1,014 | 315 | **589 (58.1%)** |
| S2 (APIs.guru) | 1,192 | 460 | 444 (37.4%) |
| pooled | 2,206 | 616 | 1,033 (46.8%) |

S1 — the peer-reviewed anchor — is the *more* concentrated of the two. Reusing a
published corpus buys comparability with Bogner, **not** diversity; Sec. 7 of the
proposal currently implies both (D-12).

## 4. Open decisions

| # | Decision | Options | Status |
|---|---|---|---|
| ~~D1~~ | ~~Provider cap~~ | **RESOLVED — D-25**: do not cap, stratify and report | — |
| **F-05** | f4 has no infrastructural-parameter exclusion, f5 does | adopt / keep + declare / report both | **open** — Sec. 6 owns the rule |
| F-02 | `norm_host()` and near-duplicates | collapse `api.`/`www.` to the registrable domain? | **open** — affects the headline corpus count |
| ~~D2~~ | ~~Oversized services (> 200 operations)~~ | **RESOLVED — D-17** | — |
| ~~D3~~ | ~~Domain-restricted null model~~ | **RESOLVED — D-18**, provider-restricted | — |

**On D1 — RESOLVED by D-25, and the answer was not the expected one.** The
question was whether the quartile thresholds move under a provider cap. **They
do**: the median falls from 0.4358 to 0.3735 at a cap of 50 and to 0.3456 at a
cap of 5, against sampling noise of 0.0012. The cause is that AWS, Google and
Azure services — **48.0%** of the primary corpus — score a median **+0.134**
higher than everyone else (Cliff's δ +0.609). The decision is **not to cap**,
because capping deletes data to hide an effect that is itself a finding, but to
**stratify the thresholds and report the difference**.

**On F-05 — raised while answering D1, and it is a defect not a property.**
Sec. 6 excludes infrastructural schemas from f5 by an ">80% of a service's
operations" rule; **f4 has no equivalent**. Google attaches six identical
parameters to 100% of its operations and AWS seven to 99%, which inflates f4 to
a median of 0.82 against 0.42 elsewhere. Applying f5's own rule to f4 would
close **46.6%** of the hyperscaler gap and affects **67.6%** of all services.
The metric has deliberately *not* been changed — see `docs/FLAGS.md` F-05.

**On D2 — RESOLVED by D-17.** Services above **200 operations** are flagged
`oversized` and held out of the *primary* analysis; every analysis is repeated on
the full corpus as a *sensitivity* check and both are reported together. Nothing
is deleted. The justification is **scope, not compute**: above ~200 operations a
specification describes an API gateway or a whole platform surface (Microsoft
Graph, Kubernetes, GitHub, Compute Engine, EC2, Stripe), not the single-capability
microservice ILSC is defined over.

The cap matters more than expected. 70 services (3.2%) hold **97.6%** of all
77,611,030 pairs — 84.0% from Microsoft Graph alone — and removing them moves
pair-weighted feature co-availability by up to **50 points** (f6: 24.1% → 74.4%)
while moving every per-service quartile boundary by at most **3.2**. See D-17 and
`results/oversized_thresholds.csv`.

**On D3 — RESOLVED by D-18.** Sec. 6 specifies a domain-restricted null model,
and no label source survived D-03 (keyword labelling rejected) and D-04 (LLM
labelling rejected). The restriction is now by **provider**, the same
substitution D-05 already adopted for the perturbation control. It validated:
E[ILSC_rand] is **0.1011** global against a **0.2370** provider-restricted
median, with 96 of 97 estimable providers above global — the restricted null is
genuinely the harder bar. A provider is coarser than a domain, so it is a
*conservative* approximation and is reported as one.

## 5. Benchmark specs

`specs/benchmarks/<system>/` holds the benchmark systems, built by
`src/benchmark_prep.py` and catalogued with their provenance in
[`results/benchmark_manifest.csv`](results/benchmark_manifest.csv).

| System | `spec_origin` | Services | Operations | **Within-service pairs** |
|---|---|--:|--:|--:|
| `sockshop` | hand-written | 5 | 27 | **122** |
| `trainticket` | generated-from-source | 34 | 211 | **794** |
| **Total** | | **39** | **238** | **916** |

Per-service Sock Shop counts (after D-07 strips `payment`'s `/health`):
user 15 ops / 105 pairs · carts 5 / 10 · catalogue 4 / 6 · orders 2 / 1 ·
payment 1 / 0. Earlier revisions of this table said **123** pairs; that counted
`payment`'s `/health`, which D-07 removes. The correct figure is **122**.

**The two systems are not interchangeable.** Sock Shop's specifications are
hand-written and independent of its source code; Train Ticket's are generated
from its source by Springfox introspection. Exp. 3 therefore reports
`rho_independent` (Sock Shop) and `rho_derived` (Train Ticket) **separately and
never pooled** — see **D-16**, which also records why no independent Train Ticket
specification exists, and why Online Boutique (gRPC, no OpenAPI at all) cannot
supply one either.

Also worth remembering:

- Every benchmark spec is **Swagger 2.0**; run them through `src/convert.py`
  before parsing.
- Sock Shop spec paths differ per service in the upstream repos:
  `apispec/user.json` but `api-spec/carts.json`. This is not a typo.
- Train Ticket ships as one combined document and is split per service on its
  `ts-*-service` tags; see [`specs/benchmarks/trainticket/README.md`](specs/benchmarks/trainticket/README.md)
  for attribution (CC-BY-4.0) and [`results/benchmark_split_log.csv`](results/benchmark_split_log.csv).

The `< 3 operations` corpus filter is **not** applied here — see DECISIONS.md D-06.
